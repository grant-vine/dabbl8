# Native three-project menu preparation

The experimental eight-track build now routes manual save, load and rename through the native shared-pool runtime after an explicit completed-migration binding. PROJECT shows three identities, A–C, while the frozen historical four-slot cache and global descriptor remain unchanged for conversion. Active UI/editor descriptors limit slot selection to three. Out-of-range native menu, graph and editor queries cannot alias an available identity.

A 64-byte target pool allocation holds trusted synchronous callbacks, a validated three-name inventory and ownership/readiness flags. Drawing reads only that cache; it never accesses flash or borrows the project/display arena for catalog work. Status identifies migration-required, ready and storage-error states. A failed catalog refresh hides stale names and marks inventory unready while retaining native ownership. Save and rename refuse before callbacks until a separate successful rescan restores current inventory. The actual SAVE action also refuses before deciding whether a slot needs overwrite confirmation, so storage recovery cannot turn a hidden occupied slot into an unconfirmed overwrite. Verified writes refresh inventory even after failure, because an error can occur after a record has committed. Live name/manual identity publish only on controller success.

Binding requires explicit completed-migration authorization, stopped transport and an inactive canvas. Unauthorized or busy attempts perform no storage access. A binding that reaches failed preflight retains native ownership in an offline state rather than falling back to historical RAM slots. Cold initialization revokes all transient callbacks and ownership. The existing-driver adapter exposes the binding entry point, but **no boot, editor or menu caller grants migration ownership**. This is integration preparation, not a device migration or release.

All eight-track legacy project/autosave writes are refused at the storage entry point before reads, erase or program, including before binding and after a cold boot. Settings and preset writes remain separate. Historical four-track behavior retains its original graph indexing and descriptor expressions. Native-owned arrangement playback refuses rather than using historical project caches; native arrangement execution is still issue #15. Native boot restore, quiet-time shared autosave scheduling, versioned native editor transfers/full backup and original-preserving physical migration remain unfinished. Expanded firmware therefore advertises no complete native backup capability and continues to reject legacy project load/save editor commands.

## Evidence and limits

The pinned JieLi builds pass. Default four-track app is byte-identical to the verified v1.1.5 baseline. Eight-track app is 456288 bytes, SHA-256 `e6f7231fb607e5f1187b6abf628c21529f37fb380f9606bdcab5a6d5f1bfd9b9`; RAM 95716/98304, pool 334164/344064, and interrupt RAM text 916 instructions/no calls. Compared with PR #66, this adds 848 image bytes and 64 pool bytes without additional normal RAM. Whole caller/driver/IRQ stack bounds and actual device deadlines remain unqualified.

Focused actual UI/native runtime tests pass 8221 checks in optimized and inherited ASan/UBSan modes. Editor dispatch checks pass 194 assertions, including three-slot discovery, fourth-slot refusal, legacy write refusal and truthful backup capability reporting. Simulated storage-gate tests prove every legacy project/autosave destination is refused before I/O while independent settings/preset writes remain possible. The physical-hook runtime tests continue to pass 217341 checks with simulated storage. An independent review identified the stale-inventory overwrite gap; the actual SAVE-path regression and refusal fix passed re-review.

Full local upstream suite passes, including both modes of the new checks and fixed-seed fuzzing. All 92 golden renders remain unchanged with zero health, voice/routing or CPU-budget failures and two existing timing notes. Default package/loader/goldens and budget files retain their hashes. Four existing omissions remain explicit: DaisySP reference, optional vendor restore simulator fixture, web editor MENU-settings subtest and local browser emulator without emcc. Logs, failed comparisons, exact source and hashes are in `evidence/2026-10-10-native-menu/`. Runtime sanitizer checks retain upstream DSP exclusions: signed overflow, shifts, bounds, object-size and pointer overflow; strict isolated storage checks do not share those exclusions. Host and simulated NOR evidence does not establish physical SPI, power-loss, installation, migration, recovery or live hardware usability. Issues #11/#12/#13/#14 remain open for their full acceptance criteria and prerequisites. No installation or download offer is made.
