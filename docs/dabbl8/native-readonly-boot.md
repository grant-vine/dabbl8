# Read-only native boot recovery

This change, based on source `e5d64a5c4f54a55a8950ea87a53ea682db154582`, connects eight-track native storage recognition to the existing `autosave_boot` caller. It is the read-only startup slice of issue #13; persistent migration, local SAVE consent, and per-operation native write authority remain incomplete and closed.

At boot, only erased sectors or historical storage containers with matching header/payload CRC and erased nonpayload bytes permit the old fallback. This checks the storage container, not its musical schema. The existing historical decoder must still accept the project body. Unknown or partial allocations suppress fallback and remain owned/offline; unknown bytes are not identified as V15 and never authorize initialization.

A complete validated native inventory can provide three saved-project names and read-only load/arrangement preparation without a USB capture or connected host. RESTORE LAST and the prior boot-clean result still control autosave recovery. Native records retain stored engines and references; missing engines or project references refuse adoption without substituting sounds. Native save and rename display `READ ONLY`; autosave is not armed. Legacy/sample/settings write quarantine and migration driver authority are unchanged.

A distinct mapped read-only session keeps erase/program unavailable even with mutation-capable physical callbacks. Each read operation validates the current native set. RAM adoption adds a pure final admission check under the existing IRQ-off boundary, including pending input/USB mutation requests, transport, owner/canvas and sounding or held notes. It leaves those inputs alone when refusing. Ordinary restoration callers pass no additional guard. Successful restore replaces the runtime arrangement cache and invalidates a suspended arrangement; skipped or refused restore retains the existing musical/cache state.

The host fixture calls actual `autosave_boot` and actual historical/native decoder and runtime paths with private NOR. Normal and strict sanitizer runner entries cover FM4/SLICE combinations. Compiled negative controls remove boot routing, final admission, or read-only mapped state. This is not full `main.c` boot, on-device timing, restore/recovery, flash-write, or stack qualification. The actual boot caller runs after audio/USB/timers/interrupts and the splash, so hardware qualification must include those live interactions.

A separate pinned FULL app-only parent/candidate build is needed to measure application/static-RAM change and stack growth. No new project-sized persistent buffer is introduced; a local 256-byte container window is not a measured stack budget. Local SAVE coordination, the original-retaining migration/initializer policy, persistent write authority and physical recovery remain separate gates. This work neither closes issue #13 nor provides permission to install firmware.
