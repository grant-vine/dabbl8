# Local native saving coordinator

This change connects local project SAVE, rename and stopped autosave to operation-specific native storage tickets. Read-only boot recognition does not grant saving permission. It does not initialize an unknown, stock, historical or damaged storage layout.

After actual project name acceptance, the first operation in a boot requires a displayed confirmation: **Saving and autosave this session**. Its proposed slot and name appear before the user presses and releases physical SAVE. Confirmation is bound to the current proposal generation and published only after the actual display sync completes and the source, USB state and quiet checks remain coherent. Holding SAVE can redraw the modal without granting permission again. Other input cancels the operation.

The resulting editing intent lives only in RAM. Each manual operation still requires fresh name-screen acceptance for that exact operation, slot and name. Each automatic operation comes from the existing stopped autosave scheduler, with its existing preference, quiet, idle and retry intervals; it captures a new proposal immediately before writing. Changing the autosave preference later does not exceed the disclosed session scope. An idle USB disconnection does not remove standalone editing intent, but a change during an operation cancels that operation. Reboot, competing migration ownership, offline storage and independently observed storage errors revoke the intent.

Before mutation, the coordinator checks the complete native inventory, references and canonical payloads, current source signature, every allocation's streamed CRC, epoch, quiet inputs and ownership. A valid autosave record is mandatory. Legitimately absent project slots require erased unused allocations or complete, canonical, strictly older native records. Sparse damaged residue never proves absence. A complete four-object recovered set retains its existing shared-spare recovery rule. All three stable project slots can be populated without a new marker, format or flash map. An interrupted sparse allocation can refuse further writing until separate original-retaining recovery re-establishes a safe spare; intact native records remain readable.

The synchronous writer checks each exact sector/page/header, unchanged target `FL_STORE_OK` bounds, a valid native block, payload buffer identity and CRC, and the operation lifetime under one existing IRQ window. It calls the unchanged RAM erase/program primitives directly. Header publication remains last; normal return is checked against actual readback. A reported failure can still follow a committed header, so an uncertain physical result revokes saving intent and leaves storage owned but offline. It never retries by inferring empty space.

The general instrument write gate remains closed. This path does not authorize historical project, settings, sample, user-preset, connected initializer or remote full-backup APPLY writes. Unknown/stock layout initialization and original-retaining migration remain separate work. Issue #13 is not complete: physical power-loss/reboot behavior, timing, verified originals retention for initialization and recovery still need qualification.

## Evidence scope

Host tests use actual calibrated UI/menu/name handling, native scheduler/runtime/storage code and private NOR spies at the real RAM primitive call sites, without a virtual permission define. They cover visible and missing confirmation, held SAVE/release, late LCD events, local save/rename/autosave, sparse creation, late automatic admission cancellation, source read/format failures, fabricated backend refusal, general-write quarantine, reentry, staging mutation and every primitive interruption. Whole NOR bytes outside the selected shared spare are compared exactly.

Initial failures and a separate strict sanitizer experiment are preserved. That experiment exposed an existing FM6 LFO signed-negative-shift and synthetic SLICE fixture bounds access; the published parent reproduces those findings. The inherited sanitizer configuration is recorded separately. No golden audio hash, global sanitizer policy or target budget is changed by this coordinator slice.

Target app-only measurement is pending review of the exact source. No target memory savings, stack high-water, audio deadline, on-device save, successful restore or installation claim follows from host tests. No firmware was flashed and no physical storage command was sent during this qualification.
