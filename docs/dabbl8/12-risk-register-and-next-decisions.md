# Risk register and next decisions

Critical risk: an eight-track format exceeds the current payload and retained RAM layout. Mitigation: maximum-size models, multi-sector save tests, reduced resident copies and an explicitly approved map. Owner decision: retain all three user sample slots or trade some space for more project/pattern capacity.

Critical risk: source assumptions in voice protection fail when tracks equal voices. Mitigation: deterministic documented stealing, bounded protection and ninth-note tests. Owner decision: preferred musical priority between drums, bass, chords and live lead; the default must remain understandable without deep configuration.

High risk: expensive engine combinations miss realtime deadlines. Mitigation: actual block profiling, caps, active-state pooling and scoped first-release guarantees. Keep an eight-FM song and a mixed-engine worst case separate in qualification; neither proves the other.

High risk: a new editor writes data an old firmware misreads, or vice versa. Mitigation: protocol family/schema handshake, max-count checks, read-only fallback and a published compatibility matrix. Version editor and firmware separately but release tested pairings.

High risk: flash/map changes weaken updates or recovery. Mitigation: unchanged loader, backup verification, complete boundary checks, power-cut simulation and a prepared hardware recovery option. Recovery not tested here is not a guarantee.

Medium risk: porting attractive features produces a confusing instrument. Mitigation: one primary workflow, original reference songs and live usability tests. Scene depth, event recording and undo should grow only as proven memory budgets permit.

Unresolved before desktop work: actual macOS and FM-1 revision; GitHub owner/repo; whether a second test unit is available; desired four versus two resident projects; sample-slot priority; external MIDI sequencing expectations; preferred track-select gesture; whether expanded FM polyphony is essential to the first release.

Recommended immediate sequence: choose the desktop workspace and repository owner; reproduce the untouched pinned Felucca build; run baseline tests; inspect generated memory reports; then implement only legacy-format freezing and automation-address tests. These produce evidence for eight tracks without immediately changing flash or audio behavior.

This pack is a starting specification, not finished firmware. Evidence in the bundle identifies exact repository snapshots and audited paths; the backlog includes acceptance gates and dependencies. Revisit live project versions before cherry-picking, but do not move the baseline midway through an unvalidated architectural change.
